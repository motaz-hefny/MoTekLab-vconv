## 3. Detailed findings

### F1 — Passthrough remux to MP4 fails on bitmap subtitles (High)

**Evidence** — `core/converter.py:1312–1319` (`_build_ffmpeg_copy_command`):
```python
out_ext = Path(output_path).suffix.lower()
if out_ext == '.mp4':
    cmd.extend(['-c:s', 'mov_text'])
else:
    cmd.extend(['-c:s', 'copy'])
```
combined with `cmd.extend(['-map', '0:s?'])` a few lines above.

**Impact** — Any MKV/MP4 whose subtitle tracks are bitmap formats (PGS from Blu-ray,
VobSub/DVD, DVB) will make the **entire** remux abort: ffmpeg cannot encode a bitmap
subtitle to `mov_text` and exits non-zero. This is a common real-world case (Blu-ray
rips), so a user choosing "Copy (Passthrough)" to MP4 can lose the whole conversion
because of a subtitle track they may not even care about.

**Research backing** — Confirmed upstream: subtitle encoding is only "text→text" or
"bitmap→bitmap"; `mov_text` is text-only. PGS/VobSub must be dropped or copied into a
container that supports them (MKV).

**Suggested approach (not a commitment)** — Probe subtitle codecs for the source
(e.g. via the existing analyzer). For MP4 output, map only text-codable subtitle
streams (`subrip`, `ass`, `mov_text`, `webvtt`) as `mov_text`, and either drop image
subs with a clear log line or refuse with a message recommending MKV. Alternatively
auto-select MKV when image subs are present.

**Suggested version impact** — patch (`10.0.1`).

### F2 — `-map 0:v?` carries cover art as a fake video track (High)

**Evidence** — `core/converter.py:1282`:
```python
cmd.extend(['-map', '0:v?', '-c:v', 'copy'])
```

**Impact** — In MP4/MOV, embedded cover art is an *actual* video stream with
`disposition.attached_pic=1` (typically MJPEG). `0:v?` selects it, so a passthrough
remux produces a second, bogus "video" track (a still cover image) alongside the real
one. The rest of the project already treats this as a known trap — see the
"MediaAnalyzer Cover-Art Stream Rule" in `AGENTS.md` and the explicit
`attached_pic` / `timed_thumbnails` skip at `core/analyzer.py:165`.

**Research backing** — ffmpeg's capital `-map 0:V` selects video streams **excluding**
attached pictures; lowercase `v` includes them.

**Suggested approach** — Use `-map 0:V?` in the video-copy path (and verify the
NVENCC/HandBrake paths already exclude attached pics where relevant).

**Suggested version impact** — patch (`10.0.1`).

### F3 — Default x265 `-x` string contains x264-only options (High)

**Evidence** — `core/converter.py:1204–1210`:
```python
if settings.advanced:
    x_opts = ':'.join(f"{k}={v}" for k, v in settings.advanced.items())
    cmd.extend(['-x', x_opts])
else:
    cmd.extend(['-x', 'cabac=1:ref=5:analyse=0x133:me=umh:subme=7:chroma-me=1:'
                      'deadzone-inter=21:deadzone-intra=11:b-adapt=2:rc-lookahead=60:'
                      'vbv-maxrate=10000:vbv-bufsize=10000:qpmax=69:bframes=5:direct=auto'])
```

**Impact** — This fallback string is x264 syntax. If a user selects an x265 encoder
**without** a preset that supplies `advanced` (e.g. manually chooses x265, or any
non-preset path), the options are handed to x265, which rejects keys such as
`analyse`, `me=umh`, `subme=7`, `chroma-me`, `deadzone-*` (and `subme` is also
out-of-range for x265). HandBrakeCLI then aborts with **exit 3** — the exact failure
described in `AGENTS.md` defaults-hardening rule #3. The new presets avoid it only
because they set `advanced` explicitly.

**Research backing** — x265 valid subme range is 0–5 (x264 allows 0–9); `analyse`,
`me`, `chroma-me`, `deadzone-*` are x264 parameters. Project rule #3 itself warns
about this class of bug.

**Suggested approach** — Make the default `-x` string encoder-aware (separate x264 and
x265 defaults), or omit `-x` entirely for x265 when `advanced` is empty and rely on
`-preset`.

**Suggested version impact** — patch (`10.0.1`).

### F4 — Passthrough progress stuck at 0% and fps never updates (Medium)

**Evidence** — `core/converter.py:1407–1436` (`_monitor_progress`):
```python
fps_pattern = re.compile(r'([\d.]+)\s+fps')
...
if 'progress=end' in line:
    ...
fps_m = fps_pattern.search(line)
```
The FFmpeg copy path uses `-progress pipe:1 -nostats` (`core/converter.py` ~line 1326).

**Impact** — `ffmpeg -progress` emits `key=value` lines and has **no percentage key**;
it reports `out_time_ms=` / `out_time_us=` and `fps=12.34` (no space before `fps`, so
the `\s+fps` regex never matches). Result: the passthrough progress bar remains at 0%
until `progress=end`, then jumps to 100%, and fps is never displayed. A cosmetic but
visible UX regression for the new feature.

**Research backing** — Confirmed against ffmpeg documentation/experiments: no `%`,
`fps=NN` is space-free, `speed=`, `out_time_*` present.

**Suggested approach** — For the ffmpeg backend, compute percent from
`out_time_us`/`out_time_ms` against the source duration (already known to the
analyzer), and parse `(?:^|\n)fps=([\d.]+)` (or `\bfps=([\d.]+)`).

**Suggested version impact** — patch (`10.0.1`).

### F5 — Queue ignores custom output dir and drops some job settings (Medium)

**Evidence** —
- `ui/main_window.py:2830`:
  ```python
  output_path = generate_output_path(input_path, format=self.format, conflict_mode='rename')
  ```
  No `output_dir` argument, so the queue computes output next to the source even when a
  custom output directory is configured.
- `ui/main_window.py:210` (`ConversionWorker._build_job_settings`) copies the base
  settings and overrides only keys present in the stored job dict; the job dict does
  **not** include subtitle settings, `metadata_preserve`, `preset_speed`, or `advanced`.

**Impact** — This is the already-documented "Queue output-path display desync" (issue
#2) plus a partial instance of "per-job settings" (issue #1). The v10.0.0 worker did
materially improve per-job isolation (job dict now seeds a deep copy), so issue #1 is
mostly closed — the remaining gap is that *some* parameters still fall back to the
start-time UI values. Net effect: a queued job can be written to a different path than
the queue table shows, and use stale subtitle/metadata/advanced settings.

**Research backing** — Direct code reading + re-confirmation of the open items listed
in `AGENTS.md` → "Known Issues / Queue Design Flaws".

**Suggested approach** — Pass the configured output dir into `generate_output_path` and
store the resolved `output_path` on the `Job`; extend the serialized job settings to
include subtitle/metadata/preset-advanced fields (or store a full
`ConversionSettings.to_dict()`).

**Suggested version impact** — patch/minor depending on scope (`10.0.1`).

### F6 — Self-update package identity check is name-only (Medium)

**Evidence** — `utils/self_update.py:122–133` (`install_deb`): runs
`dpkg-deb -f <deb> Package` and only checks that the name equals `vconv` before calling
`pkexec dpkg -i`.

**Impact** — The check confirms the package *claims* to be `vconv`, but does not verify
the bytes. A corrupted or tampered download (or a hostile mirror) that still declares
`Package: vconv` would be installed as root. For a self-updating, root-installing flow,
content verification is the meaningful control.

**Research backing** — Standard practice: verify a SHA-256 checksum (ideally a
published signature/`Release` file) of the downloaded asset against the release
metadata before privileged installation.

**Suggested approach** — Publish and verify a SHA-256 (e.g. a `checksums.txt` asset in
the GitHub release); compute the hash of the downloaded file and compare before
`pkexec dpkg -i`. Optionally also verify the Debian signature when available.

**Suggested version impact** — patch (`10.0.1`) or minor if a checksum-publishing step
is added to the release process.

### F7 — `_apply_ilst_to_moov` writes parent sizes as 32-bit only (Low)

**Evidence** — `core/converter.py:430–434`:
```python
for off, _ in update_list:
    if off is None:
        continue
    old_sz = struct.unpack('>I', moov_buf[off:off+4])[0]
    struct.pack_into('>I', moov_buf, off, old_sz + delta)
```

**Impact** — The readers (`_find_atom`, `_extract_ilst_from_file`, `_inject_ilst`,
`_apply_faststart`) correctly understand 64-bit (`sz == 1`) atom headers, but this
writer always rewrites the parent's size as a 32-bit `>I`. If `moov`/`udta`/`meta` were
themselves authored with a 64-bit size header, the first four bytes (`0x00000001`)
would be overwritten with a small 32-bit value, corrupting the atom. In practice
`udta`/`meta` are essentially never 64-bit and `moov` rarely is, so this is a
low-probability edge — but it is asymmetric with the rest of the module.

**Suggested approach** — Detect a 64-bit header at each parent offset and update the
extended-size field (`>Q` at `off+8`) instead of the 32-bit size.

**Suggested version impact** — later (low priority); needs a synthetic 64-bit test.

### F8 — Temp files can be left behind on exception (Low)

**Evidence** — `_write_bytes` (`core/converter.py:304–310`) and `_inject_ilst`
(`core/converter.py:601–620`) create `<path>.tmp.<pid>` / `.tmp_meta.<pid>` and rely on
`os.replace`. If an exception fires between `open()` and `os.replace`, the scratch file
remains.

**Impact** — Cosmetic disk litter next to the output file on rare failures. No data
loss (the real output is untouched).

**Suggested approach** — Wrap the write in `try/finally` that unlinks the temp path on
failure.

**Suggested version impact** — later (low priority).

### F9 — `check_efficiency` substring matching / codec labelling (Low)

**Evidence** — `core/validator.py:183–216`:
```python
is_heavy_audio = any(k in a_br for k in ('768', '1509', '640', '448')) or \
                 any(k in a_codec for k in ('DTS', 'TRUEHD', 'EAC3'))
```
and `is_already_hevc` includes `VP9`, whose label maps to the generic `"compressed"`.

**Impact** — Bitrate substring matching can produce false positives (e.g. a
`1448 kb/s` string contains `'448'`), and VP9 sources get a vague "compressed" label
rather than "VP9". These are advisory messages only, so the blast radius is small — a
misleading hint, not a wrong conversion.

**Suggested approach** — Parse numeric bitrates (`re.search(r'(\d+)', a_br)` and compare
against a threshold) and add an explicit `VP9` label.

**Suggested version impact** — later (low priority).
